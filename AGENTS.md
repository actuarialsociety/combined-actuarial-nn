# Agent Guidelines

`deep-actuarial-science` is a **research-paper benchmark toolkit** for deep learning in
actuarial science: each model reproduces a **named paper's published result** in a Kedro
pipeline and reports PASS/FAIL against it. Lessons (Marp slide decks in `lessons/`, also the
wiki), Colab notebooks and MLflow tracking present each reproduction. Coding agents (Claude
Code, Copilot) maintain the lessons and add models.

## Layout

| Path | What |
| --- | --- |
| `lessons/NN Title.md` | Marp slide decks (also render on GitHub and the wiki) |
| `lessons/figures/` | Figures exported from pipeline runs (`scripts/export_figures.py`); transparent PNGs styled in `plots.py` to read on light and dark pages |
| `src/deep_actuarial_science/models/` | Model code: `frequency.py`, `mortality.py`, `reserving.py` |
| `src/deep_actuarial_science/pipelines/` | Kedro pipelines: `ingest`, `frequency`, `mortality`, `reserving` (one namespace per model) |
| `conf/base/parameters_*.yml` | Data scale and model settings; `parameters_benchmarks.yml` holds published reference results |
| `conf/smoke/` | Small, fast environment for CI (`kedro run --env smoke`) |
| `src/deep_actuarial_science/findings.py` | Which gaps between models are real (paired 95% interval), where a published run falls among our seeds; each pipeline writes `findings.csv` |
| `reference/` | The frozen reference run (`scripts/freeze_reference.py`): metrics, reconciliation, findings, environment. The source of every number in the lessons and README |
| `MAINTENANCE.md`, `CHANGELOG.md` | Rules for every commit and the reference-run workflow; what changed and which results moved |
| `notebooks/` | Generated by `scripts/make_notebooks.py` (never edit the `.ipynb`); they call the pipelines via `deep_actuarial_science.notebook`, open from Colab, Kaggle and SageMaker Studio badges, run in any Jupyter (SageMaker Studio and Azure ML: clone the repo) and, in Colab, require a GPU runtime (T4) |

## Project rules (read first)

### 1. A lesson = succinct theory + a pipeline model + reconciled results

- **Theory slide is super succinct:** one or two key equations in LaTeX (`$...$`, `$$...$$`)
  and a few bullets. The code and the figures carry the lesson.
- **Core ideas panels go deeper:** right after the Theory slide, a `## Core ideas` slide holds
  5 to 7 click-through `<details>` panels (numbered ①, ②, …), each one idea with its equation
  and the exact settings the code uses. They render as collapsible panels on GitHub, in the
  wiki and in the slides (Marp `--html`). Rules: a blank line after `</summary>` and before
  `</details>`; no math inside `<summary>`; every number from a run uses a
  `<!--r:model.metric-->` marker; describe only what the code does or what a cited abstract says.
- **GitHub-safe math:** GitHub strips Markdown escapes before rendering math, so write
  `\lbrace \rbrace \thinspace \medspace \cr`, not `\{ \} \, \; \\`, and never `\%`. Display math
  is a ```` ```math ```` fence (`marp.config.mjs` turns it into `$$` for the slides); inside a
  panel it is a one-line `$\displaystyle ...$`, because GitHub skips display math in a panel
  that also has inline math. `python3 scripts/fix_math.py` applies all of this;
  `--github` renders every file through GitHub's API and fails if any span is not math (CI).
- **Every equation is labelled and explained:** a bold line above it names the model or
  quantity (`**Model: Poisson GLM for claim frequency** [1]`), and a `where …` line below it
  defines every symbol in words, separated by semicolons. The Theory slide uses
  `<!-- _class: theory -->` (smaller type) so the definitions fit.
- **Click-through citations:** cite with `[N]` against the numbered "Learn more" list;
  `python3 scripts/link_citations.py` links each `[N]` to that reference's DOI or paper page
  (CI runs `--check`). Every model label cites its academic source.
- **Visual:** every results slide shows figures produced by the pipeline (exported to
  `lessons/figures/`), never hand-drawn or invented numbers.
- **Numbers come from `reference/`:** write `⟪model.metric⟫` (or `⟪gap.<worse>.<better>⟫`,
  `⟪verdict.<worse>.<better>⟫`); `python3 scripts/fill_results.py` fills it from the frozen
  reference run, and `pytest` fails if a lesson or the README disagrees with it.
- **A ranking needs its uncertainty:** say that one model beats another only with the gap's
  95% interval from `findings.csv`; if the interval contains 0, say the test set cannot rank them.
- **Educational first:** document the logic and every model detail (architecture, loss,
  optimiser, initialisation, schedule, seeds) in the docstring and a Core ideas panel. Be
  succinct by removing repetition, never by removing what a reader needs to reimplement it.
- **Reconciled to a named paper:** every model has an entry in
  `conf/base/parameters_benchmarks.yml` with the published value, tolerance and source:
  the paper (authors, year, DOI) and the **table or figure** the value comes from. Prefer an
  original paper's table over companion notebooks or software packages, and say which one it
  is. The results slide names that paper and table. Report PASS/FAIL honestly; if no
  like-for-like published benchmark exists, say so and back-test against realised outcomes.
- **Implemented as in the paper:** where possible, follow the benchmark paper's implementation
  (data cleaning, preprocessing, architecture, loss, optimiser, training schedule, ensembling)
  and document any deviation, with its reason, in the model's docstring and the lesson.
- **Production-minded:** include the checks a pricing or reserving team needs
  (calibration, balance property, stability across seeds, look-ahead, monitoring).
- **Learn more:** 3 to 6 academic references with DOIs verified via
  `curl -s https://api.crossref.org/works/<DOI>`. Never cite from memory. Quote a paper's numbers only
  with the table or figure they come from, and describe its methods only as far as its
  abstract and those tables support. Videos are optional extras.
- Follow [`.claude/skills/build-lesson/template.md`](.claude/skills/build-lesson/template.md).

### 2. Data

- Use realistic public data with a `scale` (or companies / lines / sexes) parameter so
  experiments run small and benchmarks run at the reference setup.
- Downloads are cached in `data/01_raw` by the `ingest` nodes. Never commit data,
  `mlflow.db` or `mlruns/`.

### 3. Adding a model (the core workflow)

1. Implement it in `models/<domain>.py` with the domain's interface and register it
   (`MODELS` dict or the pipeline's `MODELS` list).
2. Add its parameter block under `<domain>.models.<name>` and, if one exists, its
   published benchmark under `benchmarks.<domain>.<name>`.
3. `kedro run --pipeline <domain> --namespaces <name>` (smoke first: `--env smoke`).
4. Full reference run of the pipeline, then `python3 scripts/freeze_reference.py`
   (writes `reference/`, exports the figures, fills the numbers).
5. Add a notebook entry in `scripts/make_notebooks.py` (with `reconciliation()` and
   `findings()` cells) and write the deck.

The dataset factories in `conf/base/catalog.yml` cover every namespace: no catalog edits.

### 4. Verify before you finish

Every commit adds a line to `CHANGELOG.md` under `Unreleased` (CI fails a pull request that
does not), and updates `MAINTENANCE.md` when a workflow, script, check or known issue changes.
Rules: [`MAINTENANCE.md`](MAINTENANCE.md).

```bash
pytest -q                                  # includes: lessons and README agree with reference/
kedro run --env smoke                      # every pipeline, ~1-2 minutes
python3 scripts/make_notebooks.py          # if notebooks changed
python3 scripts/check_links.py             # must report 0 broken
python3 scripts/link_citations.py --check  # citations click through to the papers
GITHUB_TOKEN=$(gh auth token) python3 scripts/fix_math.py --github   # math renders on GitHub and the wiki
```

`EXA_API_KEY` (lesson research) and `ANTHROPIC_API_KEY` (scheduled refresh) live in

### 7. Working principles (the maintainer's standing rules)

**Git.** Short-lived feature branches off `develop`, named per
[conventionalbranch.org](https://conventionalbranch.org/) (`feature/…`, `bugfix/…`, `hotfix/…`,
`release/…`, `chore/…`); commits per [conventionalcommits.org](https://www.conventionalcommits.org)
(`feat:`, `fix:`, `docs:`, `refactor:`, `test:`, `chore:`). Pull requests target `develop`;
`develop` is merged to `main` for a release (the wiki and slides publish from `main`).

**Code.** Modular and minimal, with few lines and thorough comments. Reusable atomic Python
objects with shared components; look for refactoring each time code is extended. Version the
package explicitly.

**Docs.** Every folder has a `README.md` with a mermaid diagram of what its code really does,
checked at push time. `MAINTENANCE.md` and `CHANGELOG.md` are updated with every change. `docs/`
holds HTML infographic pages: succinct, interactive plotly plots, click to expand, linking
straight to the systems behind them (MLflow, W&B, AWS, …).

**Reports.** Less is more and visual, with detail behind an expand. Each one states the model
version and data used, is reproducible, links to the running system, and exists as both a
report and a slide set. Expert review is extra work on top of a reviewer's day job: review tools
must be fast to use, with the ground truth easy to see.

**Scripts.** Every login and core task is a script in `scripts/`, in bash and PowerShell.

**Skills.** For each Python package used, check whether it publishes agent skills; vendor them
into `.claude/skills/` with an `update_*_skills` script.

**Kedro.** kedro-datasets, kedro-viz and MLflow. Track core metrics between pipeline steps for
audit (time, row and step totals, monetary totals). Keep notebooks that run each pipeline with
commentary for newcomers, checked against the pipelines. Settings belong in parameters.
